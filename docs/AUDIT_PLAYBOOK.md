# SEM Audit Playbook

The repeatable workflow for finding and improving stale SEM modules.
Modeled on the v1.7.0-beta.22 forecast-tracker audit ([#416](https://github.com/traktore-org/sem-community/issues/416),
commit `25575e2`) and the v1.7.0-beta.17 tariff-classifier audit
([#359](https://github.com/traktore-org/sem-community/issues/359),
commit `32a5410`).

> **The principle**: ship telemetry FIRST (zero behavior risk), then tune
> the algorithm 2–4 weeks later once new telemetry has accumulated. Never
> change behavior without a path to see what changed.

---

## When to audit a module

Pick the next candidate from [`AUDIT_BACKLOG.md`](AUDIT_BACKLOG.md), which is
regenerated by `tools/audit_candidates.py`. Higher score = more lines of code
that have sat untouched longer with more decision branches (= more
silent-failure surface area).

```bash
python3 tools/audit_candidates.py            # writes docs/AUDIT_BACKLOG.md
python3 tools/audit_candidates.py --print-only --top 30
```

## Step 1 — PROD telemetry pull

Capture how the module is **actually** behaving on a live install, not how
we **think** it behaves. Patterns by data location:

| Where state lives | How to pull |
|---|---|
| Coordinator daily storage | `ssh ha-prod cat /config/.storage/solar_energy_management_<entry>_daily` then `python3 -c 'import json; …'` |
| Energy totals storage | `ssh ha-prod cat /config/.storage/solar_energy_management_<entry>_energy` |
| Live sensor attributes | `curl -sH "Authorization: Bearer $HA_PROD_TOKEN" http://10.10.20.150:8123/api/states/sensor.sem_<name>` (mind the [login_attempts_threshold](../CLAUDE.md#ha-test-machine) ban — prefer SSH) |
| Config-entry options | `ssh ha-prod cat /config/.storage/core.config_entries | jq` |
| HA validation report | `~/bin/validate-sem.sh` |

Capture into the audit issue body verbatim. Use real timestamps; don't paraphrase.

**What to look for**:
- Distribution of decision-branch hits (which `if` / `elif` fires how often?)
- Clamped / floored / capped values pinned at their bounds
- Records with `unknown` / `None` / sentinel values
- Time-of-day capture bugs (e.g. weather recorded post-sunset shows `clear-night`)
- History entries missing fields that the code writes today (schema drift)

---

## Step 2 — Structural findings

Read the module top-to-bottom. For each decision branch, ask:

1. Could this fail silently? (no log, no exception, no user-visible signal)
2. Is the condition derived from data that's correct at this moment, or might it be stale?
3. Is there a clamp / bound / fallback hiding a real signal?
4. Does any persisted state carry a stale assumption (e.g. an enum value whose semantics changed)?
5. Does the function trust ADR conventions (sign, units, fleet vs per-charger) or duplicate them?

Cross-check against the 9 ADRs in [`docs/adr/`](adr/) — many "findings" are
just an unverified assumption that an ADR already mandates.

## Step 3 — Telemetry beta (ship FIRST)

Pure additive. Zero behavior change. The point is to make future
diagnosis a one-attribute lookup, not a debug-log session.

### Sensor-attribute pattern

Mirror [`sensor.py:2226-2310`](../sensor.py) — the existing
`classifier_path` (#359) and `dampening_path` / `correction_path` (#416)
precedents:

```python
elif self.entity_description.key == "<your_sensor_key>":
    d = self.coordinator.data
    attrs.update({
        "<module>_path": d.get("<module>_decision_path"),
        # one string per branch the code can go down
        "<intermediate_value_1>": d.get("<module>_intermediate_1"),
        # one entry per value that would help diagnose
    })
```

In the module itself, set `self._<name>_path` on every branch:

```python
if cold_start:
    self._path = "cold_start"
    return DEFAULT
if not enough_data:
    self._path = "too_few_records"
    return DEFAULT
# main path
self._path = "live_blend"
result = compute()
# clamp suffix when a bound fires
clamped = max(LO, min(HI, result))
if clamped != result:
    self._path += f"+clamped_{'high' if result > clamped else 'low'}"
return clamped
```

Then expose via `get_data()`:

```python
def get_data(self) -> dict:
    return {
        # ... existing keys ...
        "<module>_decision_path": self._path,
        "<module>_intermediate_1": self._last_intermediate_1,
    }
```

### Storage-record extension pattern

If the module persists records, follow
[`coordinator/forecast_tracker.py`](../coordinator/forecast_tracker.py)
(`DailyForecastRecord`):

- Add new fields as `Optional[<type>] = None` on the dataclass
- Write them in the record-save path
- In `restore_state`, use `record.get("new_field")` with no default so
  absent keys load as `None` — downstream consumers can then distinguish
  "never recorded" from "recorded as zero"
- Old records from pre-this-beta installs MUST load cleanly without
  exceptions

### Migration pattern

If the config-entry shape changes, add a v_N → v_N+1 step in
[`__init__.py:async_migrate_entry`](../__init__.py). The v7 → v8 from
#359 (commit `25575e2`'s prior commit) is the canonical example:

- Use the `accumulated_data` / `accumulated_options` accumulator pattern
  so multi-version upgrades don't lose earlier mutations
- Guard each step in `try/except` returning `False` on failure
- Always bump `entry.version` even when the migration body short-circuited
- Bump `VERSION` in `config_flow.py` to match
- Add a test in `tests/test_config_flow_migration.py` covering the new step
  AND update every `assert updated.version == N` to the new N (look for
  `tests/test_*_migration.py` files)

## Step 4 — Gate chain

Run in order. Each gate must pass before the next.

| # | Gate | Tool | Pass condition |
|---|------|------|----------------|
| 1 | Local syntax | `python3.12 -c "import ast; ast.parse(open('<file>').read())"` | OK |
| 2 | Focused tests | `pytest tests/test_<your_new_file>.py -q` | all green |
| 3 | Full suite | `cd /tmp/ha-config && PYTHONPATH=/tmp/ha-config python3.12 -m pytest custom_components/solar_energy_management/tests/ -q` | 0 new failures vs `git stash` baseline |
| 4 | Reviewer | `ruflo-core:reviewer` agent over `git diff` | no blockers |
| 5 | HA-TEST deploy | `~/bin/deploy-test.sh --code-only` | exits 0, 6+ validation passes |
| 6 | Live attribute check | `curl /api/states/sensor.sem_<name>` | new attributes visible, no `null`s where data should exist |
| 7 | Push | `git push origin develop` | CI 4 checks green |
| 8 | Tag | **never auto-tag** ([memory](../../.claude/projects/-home-sem-sem-community/memory/feedback_no_auto_release_tags.md)) — wait for explicit "tag it" from user |

---

## Step 5 — Soak (2–4 weeks)

Telemetry accumulates on PROD. The audit issue gets weekly comments with
distribution snapshots — pull via the same Step 1 commands but now reading
the new attributes / fields you added.

Watch for:
- Branches that NEVER fire (dead code or unreachable)
- Branches that fire much more than expected (real-world skew vs design assumption)
- Clamp suffixes appearing frequently (bound too tight, OR a real upstream signal)
- New `None` / `unknown` values in records that should have had data

---

## Step 6 — Algorithmic beta

Once the audit issue has 2+ weeks of soak data, rank improvements with
`ruflo-goals:deep-researcher`. Sample prompt template:

```
Research SOTA approaches for <module's job>. Context: <one-paragraph
of what the module does today, what PROD telemetry reveals about
actual behavior>. Constraint: pure Python, no sklearn / numpy beyond
what HA core ships with. Goal: a 5-15 line change. Cite published
sources. Rank by leverage given the telemetry data above.
```

Ship one ranked improvement at a time. Each algorithm change:

- Lives in its own beta (so rollback is one revert)
- Comes with a `tests/test_<issue>_<topic>.py` regression-lock test
- Cites the audit issue + the research sources in the commit body
- Adds an ADR in [`docs/adr/`](adr/) if it establishes a new structural
  convention (the 9 existing ADRs are the template)

---

## Step 7 — Close the audit

The audit issue closes when:

1. Telemetry surface is in production
2. At least one algorithmic improvement has shipped OR the audit's
   conclusion is "current behavior is correct, telemetry surface is
   sufficient" (this is a valid outcome — not every audit yields code
   changes)
3. The umbrella `v1.7.0 stable — systematic module audit` issue gets its
   checkbox ticked

When all umbrella checkboxes are ticked: bump `manifest.json` to
`1.7.0` (no beta suffix), CHANGELOG block in
[music-assistant style](../../.claude/projects/-home-sem-sem-community/memory/feedback_release_notes_format.md),
push to develop, ask user "tag it?".

## Anti-patterns

- **Behavior change without telemetry first.** If we can't see what
  changed, we can't know if the change was good.
- **Tightening bounds because PROD data hits them.** The bounds may be
  the brake doing its job (see [#416 comment on the May 23 fix](https://github.com/traktore-org/sem-community/issues/416)).
- **Auto-tagging a release.** Never push a tag without an explicit
  "tag it" from the user in their current message.
- **Removing the clamp / shrinkage / floor without understanding what
  inserted it.** `git log --all -S "<constant>"` first.
- **Batching unrelated audits into one beta.** Telemetry surfaces of
  3–5 unrelated modules can ride together; algorithm changes don't.
