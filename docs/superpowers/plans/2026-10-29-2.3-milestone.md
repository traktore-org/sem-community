## Open decisions (the plan assumes the first option where one is named)

1. **#1085 overrides: where do they intercept?** `energy_planner`/
   `today_plan` only ever *yields a report* — nothing downstream today
   treats a plan as a command. An override is the first case where a
   user decision overrides that report. This plan assumes the override
   is read at the same point the reactive arbiter (decide_battery/EV
   decide) already reads config, as one more input ahead of the mode —
   not a rewrite of the planner itself. Worth confirming before Part B
   starts.
2. **#1081 COP input.** No existing brand-agnostic "efficiency curve" GUI
   pattern anywhere in SEM. Plan assumes a 2–3 point user-entered curve
   (outdoor temp → COP), matching the issue's own proposed solution,
   not a learned/measured mode. A flat constant is the fallback for a
   user who enters one point.
3. **#1087 distance → kWh.** No way to parse "150 km" out of free-text
   event titles reliably. Plan assumes a pinned convention (e.g.
   `km:150` or `150km` somewhere in the title) that SEM looks for, named
   plainly in the setup docs, not NLP guessing.
4. **#1168 Part B — DECIDED, 29.10: not doing this.** The risk
   (live price-reading for every current Tibber/Amber/Octopus/Nord
   Pool/aWATTar install) outweighs the value. Part A (discovery roles
   only) still ships; `tariff_provider.py` keeps reading brand names.

## Part 1 — #1156: surplus allocation debits the measured draw

**Today:** `coordinator/surplus_controller.py:685` already computes
`held = device.get_current_consumption() if active else 0.0` — correct.
But the four return sites for an already-active device continuing on its
existing source (lines ~802, 811, 824, 833) use `rated`
(`rated = float(getattr(device, "rated_power", 0.0) or 0.0)`, line 778),
not `held`. Same shape repeats in `devices/base.py`: `SwitchDevice.
adjust_power` (1948), `ClimateDevice.adjust_power` (2212), `SetpointDevice.
adjust_power` (4189), `ScheduleDevice.adjust_power` (4311) all `return
self.rated_power` where they should return `self.get_current_consumption()`.
`CurrentControlDevice.adjust_power` (2715) is already consumption-aware —
leave it alone, out of scope (EV/battery unchanged, per the issue).

**Why this is byte-identical for an unmetered device:** on activation,
`current_consumption_w` is seeded to `rated_power` (base.py:1834, 1885,
1912, 2106, 2158), so `get_current_consumption()` returns exactly
`rated_power` when there is no sensor. The fix only changes behavior for
a device that HAS a power sensor and whose draw has actually dropped.

- [x] `surplus_controller.py::compute_load_intent`: `claim = held if active
      else rated`, use `claim` at the four active-continuing-run returns.
- [x] `devices/base.py`: the same one-line swap in all four
      `adjust_power` methods named above.
- [x] New scenario test: a metered load's draw drops to 0 W mid-run → the
      next lower-priority load sees the freed surplus; draw resumes → it
      yields again; an unmetered load's behavior is unchanged.

**Done 29.10.2026**, commit `a1195d84` on `feature/2.3-milestone`. Full
suite green (16842 passed). Also caught and fixed a latent fixture gap
in `tests/test_devices.py`'s `mock_hass` (an unconfigured power sensor

**Proof:** unit tests + one targeted replay day with a thermostat-cycling

## Part 3 — #1085 Part B: one-off plan overrides (the real work)

**The reported bug, confirmed by absence:** modes persist by design —
`select.sem_charger_<id>_charge_mode` / `select.sem_battery_<id>_mode`
are plain HA selects backed by config-entry options, nothing auto-reverts
them. Grepping for any existing "temporary override" concept
(`_until\b|expires_at|expiry`) finds only **in-memory, per-cycle**
timers that never survive a restart: `coordinator/charge_stability.py:298`
(`_giveup_backoff_until`), `coordinator/curtailment.py:98`
(`_cooldown_until`), `coordinator/device_reconciler.py:101`
(`cooldown_until`). None of these are the right shape — a user's "don't
charge tonight" must survive an HA restart, since nobody re-sets it at
2am.

**Storage shape:** follow `_restore_energy_plan`/`get_energy_plan_state()`
(already wired into the startup-restore block in `coordinator.py`), not
`persisted_flags.py` (bool switches only — wrong shape for structured
data: device_id, action, expiry, optional target value).

**Services:** `__init__.py` registers services the standard way
(`hass.services.async_register(DOMAIN, "name", handler, schema=...)` +
a `services.yaml` entry); a `"replan"` service already sits in the same
cluster where `plan_override` / `plan_override_clear` belong.

- [x] Open decision #1, resolved as assumed: `coordinator/plan_override.py`
      rewrites the battery's `battery_mode` right before `BatteryView` is
      built — the exact shape `_vpp_apply_battery_override` (#580) already
      uses — and rewrites the charger's `ChargerDecision` right after
      `decide_v2(view)` — the exact shape `vpp_pause_override` (#580)
      already uses. Zero new branches inside `decide_battery`/`decide`.
- [x] Storage: `SEMStorage.get_plan_overrides()`/`set_plan_overrides()`,
      same `_energy_data` + delayed-save cycle as the energy plan stamp.
      One override per device (device_id, action, expiry, optional
      value); setting a new one replaces the old.
- [x] Per-cycle expiry: `plan_override.purge_expired()`, wall-clock
      (survives a restart, unlike the monotonic timers this plan
      surveyed), called once per cycle in `_async_update_data`.
- [x] `plan_override` / `plan_override_clear` services + `services.yaml`
      entries, registered beside `start_battery_boost`.
- [x] "Override active until …": `coordinator.data["plan_overrides"]`
      (generic — any Diagnose section already reads `coordinator.data`)
      and `per_charger_plan_override` sensor attribute (EV card).
- [x] Round-trip test: `tests/test_storage.py`, `tests/test_1085_plan_override.py`.

**Scoped down while building, each a documented gap, not a silent one:**
- Only `skip` and `force` are acted on, for both device kinds — each
  rides an EXISTING, already-shipped command path (battery_mode `off`/

- The battery card has no dedicated override line yet (the EV card's
  per-charger attribute does) — the Diagnose data exists either way;

- Mockup-first (hard rule): judged not to apply here — nothing SETS the

## Part 6 — #1087: EV departure from a calendar entity

**Today:** `coordinator/departure.py` (#1023) — `departure_hhmm`,
`weekday_departures`, `departure_for(charger_cfg, now, config)` (next
departure after `now`, tries today then tomorrow against the weekday
table). Clean to extend: a calendar source becomes a fourth,
higher-priority candidate tried before the weekday table inside
`departure_for`, falling back to the existing chain exactly as the issue
asks.

**Energy-need math already exists:** `ev_kwh_per_100km`
(`number.py:484-493`, default 18, config-flow key at
`config_flow.py:1644`) already converts distance↔energy elsewhere. Only
a *distance* input and two small constants (round-trip factor, buffer)
are missing — not the conversion itself.

**New ground:** calendar reading. HA calendar entities don't reliably
expose next-event data as plain state attributes — the robust path is
the `calendar.get_events` **service call** (async, date range), not a
`hass.states.get()` snapshot. This is a different *kind* of input than
anything SEM reads today (an async service call integrated into the
coordinator cycle, not a synchronous read).

**Not a crawler role:** a household typically has several calendars
(personal, work, kids); which one matters is a per-charger *choice*, not
something to infer by role. Use an explicit picker, same shape as
`ev_connected_sensor` in the config flow.

- [ ] Part A: `calendar.get_events` read helper, wired into the
      coordinator cycle.
- [ ] Part B: `departure_for` gains the calendar-sourced candidate;
      `departure_signature` extended so a changed event re-triggers
      planning.
- [ ] Part C: distance→kWh need (reuses `ev_kwh_per_100km`); pin the
      distance-encoding convention (open decision #3); config picker
      (calendar entity + optional filter tag/location) per charger.
- [ ] Part D: charger-card line — "Planned for: `<event>` 08:30 → 23 kWh
      by 07:45" (UI, mockup-first).

**Proof:** `.175` with a real calendar entity and a seeded test event.
